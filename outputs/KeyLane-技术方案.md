# KeyLane 个人模型网关技术方案

> 状态：方案基线；首版实现已开始，本文仍作为目标架构和范围依据。  
> 目标：在个人 NAS 或服务器上自托管多个模型 API 账号，统一提供 OpenAI 兼容入口，并按可配置策略选择账号。网关自身的测速、管理、数据库和日志故障不得轻易影响模型请求。NAS 断网、主机停机等外部故障不在本方案的高可用范围内。

## 1. 项目目标

### 1.1 要解决的问题

- 在一个管理界面维护多个 OpenAI 兼容 API 账号。
- 把同一公开模型映射到多个上游账号，例如公开模型 `fast-chat` 对应多个供应商账号及其各自的上游模型名。
- 每次请求可按“自动择优”或“按顺序切换”策略选取账号。
- 控制单个上游尝试的超时时间、切换次数、失败阈值、账号冷却时间和测速频率。
- 让现有 OpenAI 兼容客户端只需修改 Base URL 与网关 API Key 即可接入。
- 将代理请求路径与管理面板、探测、数据库写入和日志统计隔离，避免非关键功能故障拖慢或中断模型调用。

### 1.2 第一版范围

第一版优先支持：

- OpenAI 兼容的 Chat Completions 请求。
- 非流式与 SSE 流式响应。
- 多个上游账号组成同一公开模型池。
- 自动择优与按顺序切换。
- 主动小请求测速、被动真实请求测速、请求记录和账号健康状态。
- Docker Compose 单实例部署，SQLite 持久化。
- Vue 管理面板和下游 API Key 管理。

后续可按实际账号来源增加 Gemini、Anthropic、Codex 等上游适配器。第一版不假设所有订阅/OAuth账号都能通过 OpenAI 兼容接口直接接入。

## 2. 设计原则

1. **代理优先**：模型请求经过网关时，优先保障转发；测速、分析、日志属于旁路功能。
2. **协议透明**：不重写 system/user 提示词，不修改采样参数、工具定义和模型输出内容。为选定上游所必需的字段映射除外，例如将公开模型名替换为账号配置的上游模型名。
3. **失败有边界**：只有在上游尚未向客户端提交响应内容时才允许重试或切换；已经开始输出的流不拼接第二个上游的内容。
4. **配置原子生效**：配置保存和校验成功后再一次性替换运行配置；失败时保留旧的有效配置。
5. **不把 SQLite 放在请求关键路径**：请求选路读内存快照，性能指标异步落库；数据库暂时异常时，继续使用最近一次有效配置。
6. **默认隐私保护**：不记录提示词和模型回答正文；只记录模型、账号、状态码、延迟、用量及错误分类等必要元数据。
7. **不承诺未来请求的绝对最快**：网关依据近期观测选择预计响应最快的可用账号；上游负载和网络状态变化会导致实际耗时变化。

## 3. 总体架构

```text
OpenAI-Compatible Client
        │  Base URL + Gateway API Key
        ▼
Go + Gin HTTP Service
  ├─ Proxy Data Plane
  │    ├─ Request validation / model pool lookup
  │    ├─ Account selector: fastest or ordered
  │    ├─ Upstream HTTP/SSE passthrough
  │    └─ Async metric/event enqueue (best effort)
  ├─ Control Plane API
  │    ├─ Accounts / model pools / routing policies
  │    ├─ Settings / API keys / request history
  │    └─ Vue static assets
  ├─ Probe Worker (isolated background goroutines)
  ├─ Metrics Writer (bounded queue, non-blocking for proxy)
  └─ In-memory Last-Known-Good Config Snapshot
        │
        ├─ SQLite via database/sql + modernc.org/sqlite
        └─ Encrypted upstream credentials
```

控制面（管理 API 和设置）與数据面（模型代理）使用同一个可部署服务，但分开组织代码、状态和失败处理。测速 Worker、指标写入器及请求处理协程分别有独立超时与 panic 恢复边界。

## 4. 技术栈

| 层 | 技术 | 用途与选择理由 |
|---|---|---|
| 后端语言 | Go | 单二进制部署、并发代理与流处理适合个人 NAS 服务。 |
| HTTP 框架 | Gin | 管理 API 路由、中间件、认证和静态资源托管。 |
| gowk | 选择性复用 | 评估复用其 Gin 服务启动、日志、配置或通用中间件；不让其持有代理核心状态，也不依赖其 PostgreSQL/Redis 初始化。 |
| SQLite 驱动 | `modernc.org/sqlite` | 通过 `database/sql` 接入，免 CGo，便于构建 Linux amd64/arm64 NAS 镜像。 |
| 数据访问 | 标准库 `database/sql` + 明确的 Repository | 首版表结构和查询范围可控，避免 ORM 方言差异；所有写操作经过独立写入器或事务边界。 |
| 数据迁移 | Goose（嵌入式 SQL migrations） | 版本化管理 SQLite 表结构。 |
| 上游 HTTP | 标准库 `net/http` / `httputil` 辅助，按需自定义 RoundTripper | 完整控制连接、响应头、SSE、取消、超时和重试。请求内容不经过模型语义转换。 |
| 前端语言 | TypeScript | 管理面板可维护的类型安全代码。 |
| 前端框架 | Vue 3 + Composition API | 管理界面。 |
| 前端构建 | Vite | 开发热更新与生产静态构建。 |
| 前端状态/路由 | Pinia + Vue Router | 保存管理会话状态、页面路由与表单状态。 |
| UI 组件 | Element Plus（建议） | 账号表格、配置表单、对话框和仪表盘。 |
| 前后端交付 | Go `embed` | 将 Vue `dist/` 嵌入服务二进制；NAS 上无需单独安装 Node.js。 |
| 部署 | 多架构 Docker 镜像 + Docker Compose | 适用于 amd64/arm64 Linux NAS 和普通服务器。 |

### 4.1 gowk 采用方式

本项目直接依赖 `github.com/iautre/gowk` 与其 Gin 版本，并在启动环境显式设置 `DATABASE_ENABLED=false`。gowk 关闭 PostgreSQL 后不再初始化 PostgreSQL；本应用独立以 `database/sql` + `modernc.org/sqlite` 管理 SQLite。`DATABASE_ENABLED=false` 只关闭 gowk 的 PostgreSQL 路径，不会关闭本应用 SQLite。

当前 gowk `go.mod` 声明 Go 1.27.4，Docker builder 因而固定在 Go 1.27.4。服务通过 `gowk.Run` 管理 HTTP 生命周期，并直接用 `gin.New()` 创建路由，按需挂载 `gowk.Recover()`。不使用 `gowk.New()` 默认注册的 `LogTrace()`：该中间件将完整响应复制到内存缓冲以便日志记录，可能缓冲完整模型流、增加内存占用并破坏透明 SSE。也不使用 gowk PostgreSQL 事务中间件；代理业务不需要它。

代理调度、内存配置快照、SQLite、测速队列和异步统计仍由本项目自己的业务模块负责。这样继续使用 gowk 的服务入口和 Gin 生态，同时避免其数据库默认设置与代理响应记录中间件影响数据面。

参考：[gowk 仓库](https://github.com/iautre/gowk)、[modernc.org/sqlite 文档](https://pkg.go.dev/modernc.org/sqlite)。

## 5. 代理数据面

### 5.1 下游协议

首版端点：

| 路径 | 用途 |
|---|---|
| `GET /v1/models` | 返回启用的公开模型列表。 |
| `POST /v1/chat/completions` | 代理 OpenAI Chat Completions，支持 `stream=true/false`。 |
| `GET /health` | 存活检查，不触发上游请求。 |
| `GET /ready` | 检查应用配置和 SQLite 初始化状态；代理请求本身仍使用最近有效配置。 |

后续端点可增加 `/v1/responses`、Embeddings、Images 等，前提是所选上游确实兼容对应协议。

下游通过 `Authorization: Bearer <gateway-key>` 认证。网关 API Key 与上游 API Key 分开管理。

### 5.2 请求转发规则

- 除网关认证、路由选定、公开模型名映射、上游认证头设置和 hop-by-hop 头处理外，不主动改写请求。
- 保留请求方法、兼容字段、工具定义、采样参数和调用方的其余头字段；过滤 `Connection` 等逐跳头，并由网关设定必要的 `Authorization`。
- 请求体采用有上限的流式/受控读取方式，防止无限大请求占满内存；大小上限可配置。
- 上游响应状态码、Content-Type、兼容响应头和 body 尽可能原样转发。
- SSE 按字节/数据块及时转发并 flush，不等整段完成后再发送；不缓存完整模型回答。
- 不默认记录 prompt、completion 或 Authorization 值。
- 每个请求带内部 Request ID；默认不修改传给上游的对话内容。

### 5.3 上游连接与取消

- 每个上游尝试继承下游请求的 `context.Context`。
- 客户端取消请求时，取消当前上游 HTTP 请求并释放连接。
- 连接池按 host 复用连接，并限制单账号并发，避免一个慢账号占满资源。
- DNS、TCP/TLS、响应头/首字节、流式空闲间隔、单次尝试总时长分别设置超时。
- 为每次代理请求设置整体 deadline；重试不能无限延长调用时间。

### 5.4 流式重试边界

- 上游连接失败、超时或返回可重试状态，且尚未向下游写入响应头/内容时，可以切换到下一账号。
- 开始返回 SSE 响应后，若流中断则终止该响应并记录失败；不从另一个账号续接内容。
- 对存在“上游已执行但响应没到客户端”可能性的请求，重试可能产生重复计费。该行为要通过“最大尝试数”和可重试错误策略限制，并在管理界面说明。
- 客户端取消、请求格式错误、模型不存在、下游鉴权失败等错误不应触发上游重试。

## 6. 模型池、账号和选路

### 6.1 数据结构概念

- **上游账号（Account）**：名称、Base URL、加密保存的 API Key、启用状态、并发上限、账号标签。
- **模型映射（Model Route）**：公开模型名、上游模型名、所属账号、账号优先级、可用性。
- **模型池（Model Pool）**：拥有相同公开模型名的一个或多个账号映射，以及该池独立选路策略和超时参数。
- **网关 Key（Gateway Key）**：客户端用来访问网关，可独立禁用、限流并限制可用模型。
- **探测/请求样本**：每个账号-模型组合的 TTFT、总耗时、输出速率、状态和采样时间。

同一公开模型可以映射不同 Base URL 和不同上游模型名。自动择优只在同一公开模型池内比较，避免因名称相同但能力不同而静默换模。

### 6.2 策略 A：自动择优

每个模型池可以设置为自动择优。候选账号需满足：已启用、模型映射存在、未处于冷却、并发未超限且近期健康状态合格。

选路分数基于最近样本：

- **TTFT（首字延迟）**：请求到上游首个有效响应字节/数据帧的时间。
- **生成速率**：有上游 token 用量时计算输出 tokens/s；没有用量时用流持续时间与可用 token 估算或只纳入 TTFT/完成耗时。
- **完整响应耗时**：适用于非流式或标准探测请求的完整上游耗时。
- **成功率与近期失败**：连续失败、限流或超时会降低健康分并触发冷却。
- **当前并发**：多个候选延迟相近时，优先选择较空闲的账号。

对“尽快看到输出”的场景，先按健康状态过滤，再优先选近期 TTFT 低的候选；对于固定长度探测和有实际完成样本的候选，也参考生成速度和总耗时。管理端显示使用的策略和选中原因。

调度算法建议：

1. 新账号尚无样本时进入冷启动队列，不默认永久压过已有低延迟账号。
2. 定时对候选执行小型标准探测，建立初始 TTFT/生成速率样本。
3. 每个真实请求完成后异步更新 EWMA（指数加权平均）与成功率统计。
4. 增加探索比例配置，让长期未被选中的账号偶尔得到样本；默认可关闭或设很低比例，以免影响稳定性和额度。
5. 数据量较少、多个账号分数接近或探测失败时，使用已配置优先级/轮询作为平局策略。

测速探测会消耗上游调用额度，因此频率、并发、探测 prompt、`max_tokens`、流式与非流式方式均需配置，并在面板显示预计探测行为。

### 6.3 策略 B：按顺序切换

- 管理员为模型池配置账号优先顺序。
- 每次请求从顺序首位开始；当前账号成功则返回。
- 当前尝试命中可重试错误且响应尚未提交时，按顺序尝试下一账号。
- 账号被禁用、冷却或并发满时跳过。
- 可配置账号冷却结束后的恢复行为：恢复后回到原顺序位置，或先运行一次轻量恢复探测再重新参与。
- 可配置请求失败后是否每次都重置到第一顺位，或使用 sticky/session affinity 固定会话账号。第一版建议默认每个请求从首位开始，不引入隐式会话粘性。

### 6.4 两种策略共用的错误判定

| 错误类型 | 建议处理 |
|---|---|
| DNS/TCP/TLS 错误、连接重置 | 记失败；响应尚未提交时尝试下一个账号。 |
| 连接/首字/总时限超时 | 记超时；按冷却和重试设置执行。 |
| HTTP 408、429、部分 5xx | 默认可重试；读取 `Retry-After` 并结合冷却上限。 |
| HTTP 401/403 | 标记鉴权/权限异常，可短暂隔离并减少重复打到该账号。 |
| 400/404、参数或模型错误 | 默认不重试同一错误请求；记录具体账号和上游错误类别。 |
| 下游取消 | 立即取消上游，不重试。 |
| 已开始输出后的流错误 | 结束当前流，不换账号续写。 |

实际重试状态码和异常分类需按上游特点配置，不能一概把所有 4xx 当作故障账号。

## 7. 超时、重试与健康参数

建议支持全局默认值，并允许模型池单独覆盖：

| 设置项 | 含义 |
|---|---|
| 连接超时 | 建立上游连接的最长时间。 |
| TLS 握手超时 | TLS 握手等待时间。 |
| 首字/响应头超时 | 发出请求后等待上游开始响应的最长时间。 |
| 流式空闲超时 | SSE 两个数据块之间允许的最长空档。 |
| 单次尝试总超时 | 单账号一次完整尝试的上限。 |
| 请求总超时 | 包含所有重试和切换的整体上限。 |
| 最大尝试账号数 | 一次请求最多尝试多少个候选账号。 |
| 重试次数 | 首次尝试之后允许的额外尝试次数；与最大尝试账号数共同约束。 |
| 连续失败阈值 | 连续失败多少次后进入冷却。 |
| 冷却时长 | 暂时跳过故障账号的时间。 |
| 恢复探测间隔 | 冷却期间以何种频率检查是否恢复。 |
| 探测间隔/超时 | 速度探测任务的运行周期和单次上限。 |
| 最大请求体 | 限制代理缓冲区和输入规模。 |
| 单账号并发上限 | 限制同一凭据的并行调用数。 |

超时字段需要区分“超时秒数”和“允许连续超时次数”，避免把两者混成单个选项。

## 8. Vue 管理面板

### 8.1 页面规划

1. **总览**：已启用账号数、可用/冷却账号、各公开模型池当前选路策略、最近请求成功率与延迟摘要。
2. **模型池**：公开模型列表、账号成员、选路模式、优先级和池级超时/重试配置。
3. **账号管理**：新增/编辑/启停账号，API Key 掩码展示，单账号连接测试，模型映射维护。
4. **速度与健康**：按模型池比较账号 TTFT、完整响应耗时、生成速度、成功率、样本数和最近探测时间。
5. **请求记录**：时间、公开模型、实际账号、策略、尝试序列、TTFT、总耗时、HTTP 状态和错误类别；默认不展示 prompt/completion。
6. **系统设置**：全局 timeout、retry、cooldown、probe、日志保留期、密钥轮换说明和数据备份信息。
7. **网关 Key**：创建、重命名、禁用、按模型授权和限流。

### 8.2 面板交互要求

- 账号密钥创建后只显示一次或以掩码展示，不在列表 API 返回明文。
- 保存策略前显示验证结果和会影响的公开模型。
- “测速”可手动单账号/整池运行，并明确这是一次真实上游调用。
- 请求记录展示尝试链路，例如 `Account A: timeout → Account B: 200`。
- 图表显示样本数量，不能将样本不足的估算伪装成精确速度排名。
- Vue 前端通过 `/admin/api/*` 同源访问，避免 NAS 上额外配置跨域。

## 9. 后端模块与 API 草案

### 9.1 Go 包结构

```text

internal/
  app/                    # 依赖组装、启动顺序、生命周期
  proxy/                  # OpenAI 兼容入口、请求/响应流转
```

### 9.3 持久化表草案

- `accounts`：上游账号、URL、加密密钥、启用状态、连接配置。
- `model_routes`：公开模型名、上游模型名、账号 ID、优先级和启用状态。
- `model_pools`：池级路由策略与覆盖参数。
- `gateway_keys`：客户端 Key 的哈希、名称、模型范围、限额和状态。
- `request_events`：请求级元数据、最终账号、状态、延迟与尝试次数。
- `attempt_events`：每次上游尝试的账号、错误类别、状态码、TTFT 和耗时。
- `latency_samples`：探测/真实请求样本，支持保留期清理。
- `settings`：全局配置和 schema 版本关联信息。

SQLite 配置建议启用 WAL、外键约束和忙等待上限，限制连接数并使用短事务。代理调度不等待请求事件写入完成。

## 10. 内部可靠性与故障隔离

本项目不做主机/网络层高可用，但要防止网关自身的辅助功能故障影响模型调用。

### 10.1 配置热加载

- 启动时读取数据库并校验所有模型池、URL 和策略参数。
- 构建不可变配置快照，由请求处理只读访问。
- 管理端修改通过事务持久化，验证通过后原子切换快照。
- 数据库损坏、锁定或新配置校验失败时，继续使用最近有效快照并在面板报错。

### 10.2 数据库与指标隔离

- 请求路由不在每次调用时查询 SQLite；账号/模型池配置驻留内存。
- 热路径只向有界 metrics channel 尝试投递结果，不等待写盘。
- writer 队列满、SQLite 短时锁定或写入失败时，按策略丢弃低优先级样本并计数；不阻塞响应流。
- 探测结果和真实请求统计可批量写入；配置和凭据仍需事务持久化。

### 10.3 Panic 与 goroutine 生命周期

- Gin middleware 捕获单请求 handler panic，返回标准内部错误并记录 Request ID。
- 探测、指标 writer 等每个后台 goroutine 设置恢复边界；单个任务 panic 后记录并重启该 worker，而不是终止进程。
- 所有 goroutine 受应用生命周期 context 管理，关闭时停止接收新工作并有界等待正在处理的请求。
- 不在模块间共享可变 map；并发数据使用不可变快照、锁或并发安全结构。

### 10.4 资源保护

- 有界的上游并发、请求体、SSE 缓冲和后台队列。
- 对上游响应使用流式 copy，避免将完整响应读入内存。
- 每个请求有整体 deadline；不允许重试链无限延长。
- 对下游背压采用标准 HTTP 写入和取消传播；客户端变慢/断开时停止读取上游。
- 对管理登录和网关 Key 校验设置基本速率限制，避免内部资源被单个客户端耗尽。

### 10.5 透明代理边界

透明是指不改提示词与模型语义，并尽可能保留请求/响应协议行为；选路必然需要更换上游 endpoint 和认证头，公开模型名可能需要映射成上游模型名。网关不应伪造成功响应，也不应在流已交付后静默换账号。

## 11. 安全与数据保护

- 管理端与 `/v1/*` 使用不同凭据。
- 管理密码使用 Argon2id 或 bcrypt 哈希保存；会话使用 HttpOnly、SameSite Cookie，并支持 Secure 部署。
- 上游 API Key 使用 AES-GCM 加密后存 SQLite；加密主密钥只从环境变量或部署 Secret 注入，不与数据库放在一起。
- 数据备份需要同时保存 SQLite 文件与加密主密钥；缺少主密钥时无法解密账号凭据。
- API Key 只在新增/更新时接收明文，读取 API 返回 masked 值。
- 不在日志、错误堆栈、请求历史中输出密钥或上游完整 Authorization 头。
- 默认不保存 prompts/completions；错误正文可配置为截断后脱敏采样，默认关闭。
- 建议仅暴露在 LAN/VPN；远程访问时置于 HTTPS 反向代理之后。

## 12. Docker 与 NAS 部署

- Go builder 阶段编译后端，并构建 Vue 前端资源；最终镜像只包含单个服务二进制和运行所需文件。
- 使用 `TARGETOS/TARGETARCH` 构建 amd64/arm64 镜像，运行目录挂载到 `/data`。
- `docker-compose.yml` 映射 Web/API 端口，持久化 `/data/keylane.db`，注入管理密码、网关 Key 与加密主密钥。
- 提供 `/health` 供容器自检和 `/ready` 供启动顺序确认。
- 容器启动时运行 SQLite migrations；迁移失败要停止接收流量并保留数据库原件，不自动删除或重建数据。
- 提供备份/恢复说明与版本升级步骤；备份时协调 SQLite checkpoint 或使用 SQLite backup API。

## 13. 开发阶段

### Phase 1：骨架与代理最小闭环

- OpenAI-compatible 账号 CRUD、公开模型列表、Chat Completions 非流式/流式透传。

### Phase 3：可靠性与运维面板

## 14. 第一版验收标准

- 多个上游账号能映射到同一个公开模型，客户端只需使用一个 Base URL 和一个网关 Key。
- 流式和非流式 Chat Completions 均可代理；流式输出不被完整缓冲。
- 用户能分别设置自动择优和按顺序切换，并能修改超时、重试次数、尝试账号数、失败阈值与冷却时间。
- 自动择优基于同模型池近期测速与真实请求的模型响应数据；面板能看到样本数量和选路依据。
- 可重试错误在响应提交之前按配置切换；响应已开始后不续接其他账号。
- SQLite 短时不可写、日志队列满或测速任务出错不会阻塞已有代理请求。
- 配置修改失败或无效时，运行中继续使用旧的有效配置。
- 上游密钥不以明文写入 SQLite 或日志。
- Docker 单实例可在持久化目录下重启后恢复账号、策略和统计信息。

## 15. 风险与明确限制

- **响应“最快”只能估计**：探测请求和真实 prompt 的长度、缓存状态、上游负载不同；网关依据历史观测选预计最快者，无法保证未来单次绝对最快。
- **测速消耗额度**：频率越高，排序更新越快，但会增加调用次数。要有默认保守频率和按池关闭选项。
- **重试可能重复产生上游费用**：网络错误发生时，上游可能已执行请求但响应尚未到达；重试预算需可控。
- **流式开始后不可安全切换**：一旦有内容到达客户端，不能无损换账号。
- **SQLite 适合个人单实例**：如果未来需要多副本共享状态或高并发写入，再迁移 PostgreSQL/Redis；第一版不引入这些服务。
- **gowk 的依赖条件需确认**：在确认 License 与 API 后再决定复用比例；网关核心采用独立包结构，避免框架层限制后续维护。
